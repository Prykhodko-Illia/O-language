3. Prompt (my language design, pasted as written):
   "Types & Literals
   * i32: `doze` (standard 32-round capacity)
   * i64: `fawty` (extended capacity / drum)
   * bool: `line` (binary territory state: clear or compromised)
   * true literal: `merch` (strictly sworn, verified truth)
   * false literal: `woof` (false claims, barking without backing)
   Variables & Storage
   * Declaration shape: `tuck <identifier>: <type>`
   * Mutable marker & placement: `sliding` prefix (`tuck sliding <identifier>: <type>`). Immutable by
     default (`tucked`).
   * Assignment operator: `post` (binds a value to a register/identifier; e.g., `x post 100`)
   Operators
   * Arithmetic: Add: `bump`, Subtract: `tuck_in`, Multiply: `double_back`, Divide: `breakdown`,
     Modulo: `scraps`
   * Equals operator: `in_tune` (`a in_tune b`)
   * Not-equals operator: `fugazi` (`a fugazi b`)
   Control Flow & Blocks
   * if keyword: `spot`
   * else keyword: `pivot`
   * Block open / close: `creepin { ... } ghost`
   * Return statement: `cuh` (returns value or exits current frame; e.g., `cuh 0`)
   * Exit / Abort statement: `scat` (immediate process termination/panic)
   * Statement separator / line rule: `no_bap` (strictly required terminal delimiter)
   Unique Feature & Extras
   * Unique syntax feature (`on_the_guys` invariant): Compile-time or runtime contract
     verification. Evaluates the enclosed condition; panics immediately if the state evaluates
     to `woof`.  on_the_guys(target in_tune 40) no_bap
   * Extras:
     * Function declaration: `drill <fn_name>(<params>) cuh <return_type>`
     * Line comment: `lowkey // commentary`
     * Block comment: `huddle /* ... */`
     * Print / stdout: `air_out("message") no_bap`
   Example Routine
   drill run_check(target: doze) cuh bool creepin {
       tuck sliding counter: doze post target no_bap
       spot (counter fugazi 0) creepin {
           counter post counter tuck_in 1 no_bap
           on_the_guys(counter in_tune 0) no_bap
           cuh merch no_bap
       } ghost pivot creepin {
           air_out("empty") no_bap
           cuh woof no_bap
       } ghost
   } ghost
   this style
   main rule: DO NOT INCLUDE YOURSELF IN COMMIT AUTHOR's"

   What the AI did:
   Checked the design against the PDF's required features (all present) and decided the open
   points, which I accepted:
     - `cuh bool` in my example became `cuh line`, because the bool type is `line`;
     - `tucked` is not a keyword: a declaration without `sliding` is immutable;
     - every declaration needs `post <expr>`;
     - a block is `creepin { statement+ } ghost` and is never empty (changed in prompt 5);
     - `no_bap` ends simple statements; `spot` and `drill` end with their block and take none;
       newlines are just whitespace;
     - `lowkey` starts a comment to the end of the line; block comments (`huddle`) were left out
       because the design gives no way to close them;
     - `( )` group expressions, so `spot (x fugazi 0)` and `spot x fugazi 0` both work;
     - overflow: a number above the fawty (i64) maximum is a lexical error; checks that depend on
       the type are left for stage 2.
   Then wrote, borrowing the structure of my practice code:
     - src/lexer.py: new byte state machine (START, WORD, NUMBER, STRING, COMMENT) producing one
       token stream with an eof token instead of a list of lines;
     - src/ast_nodes.py: ASTNode / ProgramNode / FunctionNode / StmtNode / ExprNode hierarchy with
       dump();
     - src/parser.py: recursive descent with peek/eat, one method per grammar rule;
     - compiler.py with --ast and --tokens; src/errors.py copied from my practice;
     - grammar.ebnf;
     - 21 valid and 30 invalid test programs with expected outputs, and run_tests.sh;
     - README.md.
   The expected files were generated by running the compiler and then checked by reading every
   error line and the AST dumps.
   No commit has the AI as an author or co-author.

8. Prompt (I pasted a review of weak spots, written by another AI chat, and asked to fix them):
   "solve it and update ai_usage.txt
   Weak spots a strict grader could mark down (Language design, 4 pt)
   3. The "unique syntax element" is weak. `on_the_guys(...)` is an assert keyword, which is a
      new word, not new syntax. The PDF's examples are things like "one symbol per line" or
      "inverted lines".
   4. Overflow is only checked against the i64 maximum. `doze x post 3000000000 no_bap` parses
      fine. Leaving the i32 check for stage 2 is defensible, and the README explains it, but a
      grader could still call it partial.
   5. Tokens aren't written out in EBNF. `ident`, `number` and `string` are only described in a
      comment. "Every construct your parser accepts is in the grammar" can be read strictly, and
      adding three small rules would close that gap."

   What the AI did:
   - Unique syntax: added inverted lines. A line opened with `pab_on` ("no_bap" backwards) holds
     a declaration, assignment, cuh or scat written back to front and ends with the line:
         pab_on 5 post x doze sliding   =   sliding doze x post 5 no_bap
     The lexer emits an `eol` token at the end of a line opened by pab_on (the only place a
     newline matters), the parser has a parse_inverted method and grammar rule, and the dump
     marks the node "(inverted)". on_the_guys stays as the assert statement.
   - Overflow: when a doze or fawty variable is initialised with a constant expression (numbers
     and operators only), the parser computes its value and checks it against the type's range
     (doze -2^31 .. 2^31-1, fawty -2^63 .. 2^63-1); a constant division by zero is an error too.
     Values involving variables are still left for stage 2.
   - EBNF: added rules for the tokens: ident, number, string, eol, comment, letter, digit, and
     what separates tokens.
   - 13 new tests (3 valid, 10 invalid): 69 in total, all passing. README updated with a section
     for each change.
